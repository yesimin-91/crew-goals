# Crew Goals 开发计划 v2

## 文档目标

- 把 `docs/PRD_v2.md` 转成可执行、可审查、可持续迭代的开发方案。
- 统一开发、联调、code review 和验收时的判断标准。
- 明确当前阶段的产品目标是补齐 Crew Goals 的 MVP 闭环，而不是扩展到历史系统、社交能力或多目标体系。

## 当前基线

- 代码库已经具备部分读模型、后端领域服务和部分页面展示。
- 当前缺口集中在创建流程、邀请动作、运动后贡献卡、结果页和 restart 闭环。
- 第二阶段的重点不是重写已有实现，而是在现有模块边界内补齐缺失链路，并把规则收敛到服务端。

## 第二阶段目标

- 让用户可以完整完成一次 Crew Goals 主链路。
- 让用户可以从 Home 或 Goals Hub 进入创建流程。
- 让被邀请者可以真正接受或忽略邀请。
- 让活动同步后可以展示贡献结果、重复去重和不符合条件的原因。
- 让 Completed 与 Expired 都有明确结果页，并支持 Start Another Goal。
- 让分享、埋点和通知预览至少具备可验证的工程落点。

## 范围边界

### 明确纳入

- 创建 7 天 Distance Goal
- 选择 1 到 3 位好友
- 推荐距离计算与预览
- 邀请接受与忽略
- Goal Detail、Post-run、Completed、Expired
- Restart 预填逻辑
- 关键埋点
- 通知预览

### 明确不纳入

- 实时同跑
- 实时位置
- 聊天
- 陌生人组队
- 排行榜
- 勋章
- 个人最低配额
- 自定义目标输入
- 多目标类型
- 社交 feed
- 点赞和评论
- 完整历史目标列表

## 使用方式

- 开发前先看这份总览，再进入对应子文档。
- 开发时优先查看前端或后端方案，避免在页面里重复写业务规则。
- 审查时优先查看交付方案和审查指南，按验收标准判断是否真正满足 MVP 闭环。
- 如果实现和 PRD 冲突，以 PRD 为准；如果实现和本计划冲突，以本计划中的收敛规则为准。

## 共同原则

- 服务端负责业务真相，前端负责表达与交互。
- 时间、状态、可加入性、可计入性、结果锁定都必须由服务端裁决。
- 页面只消费机器可读的状态，不在前端重复实现复杂规则。
- 所有关键写操作都要考虑幂等、事务和并发。
- 移动端体验优先，桌面只作为开发预览环境。

## 审查视角

- 这套文档不是展示型设计稿，而是开发和 review 的事实依据。
- 任何新页面、新接口、新状态机都应该能在这些文档里找到对应位置。
- 如果某个实现点无法在文档中定位，说明文档需要补充，或者实现范围已经偏离计划。
